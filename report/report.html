Task 1: Object storage and parallel teacher labelling

Setup. The cluster is created from cluster/k3d.yaml (port 8080 to Traefik, 8333 to the S3 NodePort). SeaweedFS runs as one Pod in namespace data (master, volume, filer and S3 gateway in one process, PVC on local-path). S3 credentials are generated into a git-ignored .env and loaded into Secrets by scripts/secrets.sh. scripts/s3_setup.py creates the buckets datasets and models and uploads commands_pool.jsonl. The teacher (phi3.5 in Ollama, temperature 0, seed 42) runs on the laptop to use its GPU; workers reach it through host.k3d.internal. The few-shot prompt is prompts/teacher_prompt.txt (examples taken only from the handout, none from validation).

Sharding. Worker k of N processes the commands whose 0-based line number n satisfies n mod N = k. Every n has exactly one remainder, so the shards are disjoint and together cover the file, with no coordination between workers. Round-robin assignment also balances the shards (1,500 each for N = 2) even if command difficulty drifts along the file. Each worker writes only its own object datasets/teacher/shard-k.jsonl, so there are no write conflicts. Progress is flushed every 25 records, and a restarted worker skips ids already stored, so a crash costs at most 25 teacher calls. Two Jobs (teacher-shard-0/1, SHARD_COUNT=2) ran at the same time in namespace pipeline (about 47 minutes, 0 restarts). Check: 3,000 ids in the shard outputs, 3,000 unique, identical to the pool.

Cleaning (worker/clean.py; rejects checked in the order a–e; output in id order; checksum d0f4fc58…752d, reproduced by python worker/clean.py --local datasets/teacher):

3,000 = 589 + 0 + 4 + 138 + 31 + 2,238. Nearly all (a) rejects are a correct JSON object followed by a note (“(Note: …)”); they are rejected because replies are stored exactly as generated.

Problem found. phi3.5 sometimes generated thousands of tokens (Ollama log: n_gen = 2417), which blocked both workers. I added num_predict: 128 (a valid reply needs about 30 tokens), deleted the partial shards and relabelled everything, so all 3,000 replies come from one configuration.

Task 2: Training the student (sequence-level distillation)

Setup. make train runs training/train.py, which reads only training/config.yaml (seed 42, learning rate 3e-4, batch 16, 8 epochs, max length 96, library versions; the seed and deterministic algorithms are set in code). Each example is Command: <text>\nJSON: <teacher reply><eos>, and the loss covers the reply tokens only. The first 1,500 cleaned records are used; make train SUBSET=50 trains on 50 (about 2.5 minutes). Loss per epoch is in training/loss.csv (0.619 → 0.009). v2 (training/config_v2.yaml: seed 43, 10 epochs) is in training/loss_v2.csv. Model and tokenizer files are in s3://models/v1/ and s3://models/v2/. scripts/publish_model.py builds a deterministic tarball; its SHA-256 is stored as models/v1/model.sha256 and equals the checksum of the GitHub Release asset model-v1.tar.gz (4cffa3eb…85aa; CI checks it with sha256sum -c).

Suitability of Pythia-70M. It is small enough to train on a CPU (about 1.5 minutes per epoch) and to serve within 1 CPU / 1 GiB, and its GPT-NeoX tokenizer handles JSON punctuation. It has no instruction tuning and little world knowledge, so untrained it produces no valid output at all (table below); everything it does here comes from fine-tuning on one narrow format.

What changed. Fine-tuning took Pythia from 0% to 100% JSON validity. The student even beats the teacher on full frame (48 vs 41), mainly because it was trained only on replies that passed cleaning: it never learned the teacher's habit of adding notes (25% of teacher outputs on validation were invalid), and the copy-from-command filter removed invented slots. Where the teacher is consistently wrong (for example date: "this afternoon"), the student copies the mistake. v2 trained longer and fits the training set more closely (final loss 0.004) but scores lower, a sign of overfitting, so v1 is deployed.

Sequence-level versus logit-based distillation

  • Sequence-level (Kim and Rush, 2016), used here: the student is trained with ordinary cross-entropy on the text the teacher generated (its decoded output sequence), treated as hard target tokens.
  • Logit-based (word-level) distillation trains the student to match the teacher's full probability distribution over the vocabulary at every position (soft targets, usually a temperature-scaled KL divergence), which also carries information about the alternatives the teacher considered.
  • Why it is not possible here: Ollama returns only the generated text, not per-token distributions. phi3.5 and Pythia also use different tokenizers and vocabularies (about 32k vs 50k tokens), so there is no token-by-token correspondence to match even if the logits were exported; and it would require running both models together during training.
  • Limitation of this approach: the student can only be as good as the teacher's single greedy answer. Teacher errors that pass the cleaning filters (wrong intent, wrong but present slot text) are learned as truth, and the commands whose replies were invalid are simply lost, which biases the training data towards commands the teacher found easy.

Task 3: The inference service in a container

Design. FastAPI (service/app.py) on port 8000. At start-up a background thread downloads every file under MODEL_URI from S3_ENDPOINT (credentials from the Secret s3-credentials via envFrom) and loads the model. /readyz returns 503 until then, /healthz always 200; a failed load exits the process so Kubernetes restarts it. POST /parse runs greedy generation (MAX_NEW_TOKENS, one thread, one request at a time), keeps the first line and validates it against schema.json with jsonschema. Invalid output returns HTTP 500 {"error": "invalid_model_output"}, never broken JSON with 200. Headers: X-Model-Version = MODEL_VERSION, X-Served-By = Pod hostname. FAULT_INJECT=1 replaces the output with not json before validation.

Image. python:3.11.10-slim, CPU-only PyTorch wheel, every package pinned (service/requirements.txt is the full pip freeze), no weights, non-root user; 1.27 GB. Built with one command: make image.

Measured (results/limits_test.txt, results/fault_inject.txt): docker run --cpus 1 --memory 1g, 50 sequential requests: 50 × HTTP 200, OOMKilled: false, peak memory 576 MiB (sampled with docker stats). With FAULT_INJECT=1 in the cluster: HTTP 500 with the exact error body.

Limitations. The whole cluster runs on one laptop inside one Docker VM. The two “nodes” are containers on the same machine, so this shows Pod-level self-healing, not fault tolerance across machines; losing the laptop loses everything, including the single-replica SeaweedFS. Cold start is short because the image is pre-imported on the nodes and the 280 MB model comes from in-cluster storage [ASSUMPTION: a registry pull and remote storage would add tens of seconds]. metrics-server needs about a minute before the HPA sees CPU (FailedGetResourceMetric events at start). With at most 2 replicas and a 1-CPU limit, scaling can only double capacity. To get exactly two Ready replicas for a test, the scripts set HPA minReplicas to 2 temporarily and restore it afterwards.

The working is in network/subnets.md (smallest prefix with 232−p − 2 ≥ hosts, largest first, contiguous). NACL for the public subnet (network/nacl.json): inbound 100 deny all from 198.51.100.0/24; 110 allow TCP 80 and 120 allow TCP 443 from 0.0.0.0/0; 130 allow TCP 22 from 10.20.5.128/27; 140 allow TCP 1024–65535 from 10.20.0.0/22 (app replies). Outbound 100 allow TCP 8000 to 10.20.0.0/22; 110 allow TCP 1024–65535 to 0.0.0.0/0 (replies to clients). Everything else hits the default deny. nacl_sim.py --check on the sample packets: 6/6.

Why replies need their own rules. A NACL is stateless: it does not remember that a connection was opened, so every packet, including a reply, is checked on its own. The response to a client's request on port 443 leaves towards the client's ephemeral port, and the app's answer to the load balancer arrives on the load balancer's ephemeral port, so both directions need explicit rules for 1024–65535. Why order matters. Rules are evaluated from the lowest number and the first match wins. A packet from 198.51.100.9 to port 443 also matches allow rule 120; the deny works only because its number (100) is lower than every allow rule it must override.

Task 6: Reproducibility, testing and CI/CD

make up (venv, cluster, SeaweedFS with buckets and data, service image imported into k3d, models v1/v2 into S3 from local artifacts or the GitHub Releases, deploy) brings the system up after git clone and cd: three commands in total. make down runs k3d cluster delete. The workflow .github/workflows/ci.yml runs lint (ruff) → unit tests (8 pytest tests: rejection reasons and counts, duplicates, shard coverage, API headers, FAULT_INJECT, schema rejection, probes) → evaluate (downloads the model tarball from the GitHub Release, checks its SHA-256, runs predict.py and score.py on validation.jsonl) → quality gate (score.py --min-validity 95), plus a gitleaks scan of the full history (no leaks). The run for model-v1 passed every stage. The gate was shown working with the untrained Pythia-70M, published as release model-bad: run https://github.com/Nitheesh-Purnanand/cloud-computing-assignment/actions/runs/42552350446 passes lint, tests and evaluation and fails at the quality gate with QUALITY GATE FAILED: json_validity 0.0 < 95.0. AI use is described in AI_USE.md.

Task 7: Performance, cost and review

Measured with the standard Locust command through the Ingress, 2 Ready replicas (results/loadtest_stats.csv, loadtest_top_pods.txt): 222 requests (CSV; the console summary shows 224), 0 failures (error rate 0%), p50 2,100 ms, p95 2,500 ms, 1.87 requests/s; each Pod about 997m CPU (at its 1-core limit) and 464–545 MiB memory; cold start median 2 s (Task 4).

Cost (rate card, billed on limits): one replica = 1 vCPU × 3.50 + 1 GiB × 0.45 = 3.95 INR/h; two replicas = 7.90 INR/h. Requests per hour = 1.8713 × 3,600 = 6,737. Cost per 1,000 requests = 7.90 / 6,737 × 1,000 = 1.17 INR. [ASSUMPTION: only the parser replicas are billed; SeaweedFS, the control plane and the teacher are excluded.]

SLO. 99% of POST /parse requests return HTTP 200 within 30 s, over one standard load-test run. Error budget = 1% × 222 = 2.22, so 2 failed requests are allowed; 0 were used (0% of the budget). In the rolling-update run the same SLO allows 3 failures out of 395; 1 was used (33%).
